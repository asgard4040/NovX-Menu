# WhatsApp delivery ordering

Delivery extends the existing authenticated Gupshup/Meta ingress, durable queue,
bounded AI classifier and shared pending-order writer. It does not add another
order lifecycle. Waiter review and kitchen transitions remain the existing flow.

Production release: November 19, 2026 (Baghdad time), deployment
`dpl_2BdK9d8aAqvRE9LrUUGVdAJkyzmL` on `rest.ordova.cc` and `menu.ordova.cc`.
The delivery migration was applied, service-role/RLS checks passed, and the
authenticated owner settings section was verified live. All 58 focused WhatsApp
tests passed in the isolated release checkout; TypeScript and the production
build succeeded. Delivery remains off and coverage is empty until an owner
configures it. No paid live messages or customer orders were created for release
verification.

## Owner setup

In the owner dashboard, open **WhatsApp AI → Assistant settings → Delivery ordering**.
Add each actual **city**, **area**, and **fee in IQD**, then enable delivery,
WhatsApp ordering, and the assistant. Save settings. Zero means explicitly free
delivery for that zone. Delivery is disabled by default; no areas or fees are
preloaded or inferred. Owners can change coverage and fees at any time; existing
unconfirmed quotes must be repriced and confirmed again.

The existing opening/closing settings apply to ordering hours. Owners and ORDOVA
admins use the existing authorized settings API; other tenants cannot edit them.
Up to 100 zones are supported, with unique IDs, city/area validation, and bounded
nonnegative fees. No new API credentials or environment variables are needed.

Coverage uses exact normalized configured area names, with city disambiguation
when necessary. It does not infer coverage from an AI-selected zone, a guessed
fee, or an unverified map pin. Alias names are not automatically geocoded. Missing
or ambiguous coverage fails closed and asks for city/area clarification or staff.

## Customer flow

1. The classifier resolves products and quantities from the current tenant's
   bounded menu context. Backend pricing validates availability and options.
2. Delivery is the default when enabled, while explicit pickup remains supported.
3. The assistant asks for the area and nearby landmark only if missing. It can
   extract a literal address span from a complete order message; invented spans
   are rejected. A short area-only answer prompts for the street or landmark.
4. The assistant confirms use of the authenticated WhatsApp sender number or
   requests an alternative. Explicit preferences and valid contact numbers sent
   upfront are retained, rather than requested again.
5. The backend generates a full summary using current item prices and the
   owner's verified zone fee, address and delivery contact choice.
6. Confirmation creates one normal `pending` ORDOVA order and only then queues
   the actual order number. The waiter can approve/reject it normally; kitchen
   ready notifications say ready for delivery. This does not claim dispatch,
   payment, delivery completion or an invented preparation estimate.

The waiter sees delivery address, contact phone, fee and optional shared-location
link on the existing order card. Kitchen cards identify delivery orders without
adding contact details to their display.

## Phone and location provenance

The official Gupshup V2 phone fields are `payload.source` and
`payload.sender.phone`. Both are checked for consistency when present. Newer
BSUID-only events can instead contain `sender.userId`/`sender.user_id` and no
phone. A Business-Scoped User ID is never converted into a phone number.

Authenticated ingress stores a normalized `whatsapp_sender_phone` server-side.
Phone choice uses this value directly, without a model call. An alternative is
stored separately in `delivery_state.deliveryContactPhone`, with
`deliveryPhoneSource=alternative`; it never overwrites the sender field.
Authoritative sender changes invalidate an active quote, and authenticated
identity-change events clear the old sender phone until a new one is supplied.

If WhatsApp hides the phone, the assistant explains that and requests a typed
delivery contact. It cannot fulfill “same number” from a BSUID alone. Local Iraqi
`07XXXXXXXXX`, Arabic/Persian digits, international `+country...` and `00country...`
formats are normalized and checked; this validates format, not ownership or
reachability. The model cannot supply a phone, source flag or delivery charge.
The SQL update boundary also checks that an alternative number came from the
current customer text and was requested in the current phone-collection context
or supplied with an explicit contact marker.

Gupshup `location` messages carry `payload.payload.latitude` and `longitude`,
optionally `address`. Coordinates are parsed and range-checked server-side, not
generated by the model. A pin alone is not treated as a verified delivery address
or coverage proof; the assistant still requests the missing area/landmark.
No phone numbers, addresses or raw webhook payloads are added to operational logs.

References: [Gupshup text/sender fields](https://docs.gupshup.io/docs/text),
[Gupshup location payloads](https://docs.gupshup.io/docs/other),
[Gupshup BSUID behavior](https://support.gupshup.io/hc/en-us/articles/55873677826713-Username-Business-Scoped-User-ID).

## State, confirmation and database changes

Apply `supabase/migrations/20261119005031_whatsapp_delivery_ordering.sql` after
the previous WhatsApp migrations, before deploying this code. It adds only:

* `whatsapp_settings.delivery_enabled` and `delivery_zones`.
* `whatsapp_conversations.whatsapp_sender_phone` and `delivery_state`.
* Service-only delivery-state/pricing functions and extensions to the existing
  ingress, completion, status-notification and admission functions.

Existing RLS and tenant relationships remain in effect. The state records cart,
address, contact choice and the missing field. Every change invalidates the old
summary. Final SQL checks tenant/conversation, account, lease, subscription,
ordering hours, delivery enablement, products/options/prices, address, coverage,
phone, fee, total, expiry and quote receipt before invoking the existing shared
order writer. Delivery metadata is stored on the existing order; item lines keep
their real prices and the order total includes the delivery fee.

“إي”/“إي ثبت” can confirm only while explicitly awaiting confirmation of the
active summary. SQL requires that the incoming message was received after that
summary was queued, and the summary has an accepted/sent receipt (or a matching
button proves receipt for an uncertain send). A prior queued “yes”, an unrelated
reply, stale button or model tool output is not authorization. Price/availability,
coverage or fee changes require a new summary and fresh confirmation. The same
confirmation phrase is allowed for a newly revised quote; rate limits still apply.

Quote-ID uniqueness, job leases and existing webhook-ID deduplication prevent
duplicate orders. A simulated database insertion failure rolls the whole order
transaction back, emits no false success, and permits a safe retry. Existing AI
cost limits, scope controls and service-window checks remain in place. Draft
contact/address state is cleared on cancellation or successful submission, and
inactive draft state is pruned after 30 days with the existing cleanup job; the
confirmed order retains the details required for fulfillment under ORDOVA's
existing retention workflow.

## November 19 confirmation and latency fixes

The 04:51 Baghdad conversation exposed Self-Serve `button_reply.payload.id`
being treated as unsupported. Both documented `id` and legacy `postbackText`
now map to the existing server-validated quote confirmation token. Conflicting
values fail closed; visible button titles never authorize an order.

Informational replies preserve an active delivery quote. Asking whether an
order was confirmed does not confirm it. Current-cart questions and fresh
ordering requests after 30 minutes of inactivity use deterministic handlers;
a fresh request clears the stale unsubmitted draft. A standalone valid phone
line in a complete order is validated on both the application and SQL boundary.

Authenticated incoming events wake the same leased worker using Vercel
`waitUntil`, after a 350 ms batching window (450 ms wake delay). Webhooks still
persist before acknowledging. Cron remains recovery for interruption and retries.
No paid message replay is attempted. The new job_timing log contains queue and
processing duration, IDs and direction only; no message content or credentials.
Provider/network/model time and cold starts still affect end-to-end latency.

New runtime dependency: pinned `@vercel/functions` 3.11.3. No new environment
variables, credentials, quotas or owner setup are required. Production uses its
existing `VERCEL=1` platform environment flag.
